The headline number, stated plainly because it is the one that matters: the platform does not fit on one node. docs/resource-budget.md holds the arithmetic — 3850m / 4688Mi of requests against 1830m / 3741Mi schedulable = 210.4% CPU and 125.3% RAM, of which 2820m is the boutique namespace's own request, not the observability stack (Phase 11 added Tempo at 250m/512Mi and the collector's 128Mi → 192Mi per replica; before it the numbers were 3600m / 4048Mi = 196.7% / 108.2%). The fix is architectural: all four nodes are schedulable, the k3s servers carry no control-plane taint, because with a hard 8-vCPU quota there is no separate worker fleet to pair a control plane with (kubeadm control-plane nodes are schedulable by default; EKS taints them). On the deployed shape that is 7320m / ~6960Mi schedulable — 53% CPU and 67% RAM, roughly half the cluster free on both axes. The single-node arithmetic stays in the repo deliberately: it is the regression bound the gate enforces, not a description of what is deployed.

Waves D — 2026-10-14, the edge answered, and the address under it moved

Traefik was installed and every ALB target read Target.Timeout. Six defects, every one of them found by measuring the live path rather than re-reading the plan, and every one fixed in source.

D1 — the NodePort security-group rules were written backwards. Both rules sat on boutique_edge *sourced from* boutique_node_internal, which is a rule permitting the nodes to reach the ALB on 32080/32443: a path nothing uses. The ALB's own forwards and health checks originate from the edge group, and they were refused. An ingress rule belongs to the group that receives the packet. Measured after the fix, on the receiving group:

$ aws ec2 describe-security-group-rules --filters Name=group-id,Values=sg-010db8487b424e326
  32080  32080  tcp  sg-0740958ab70774ffc     <- the ALB
  32081  32081  tcp  sg-0740958ab70774ffc
  32443  32443  tcp  sg-0740958ab70774ffc

D2 — the same group's egress was 443 and DNS only. Direction on the node is half of a handshake. boutique_edge allowed outbound 443 to the world and 53 to the resolver, and nothing to the nodes, so the ALB's health checks were dropped at the source no matter what the node answered. Three egress rules, one per port, rather than a 32080-32443 range that would become implicit permission for every future NodePort.

D3 — the health check asked a question the entrypoint cannot answer with 200. It probed GET http://<node>:32080/ping expecting 200. Port 32080 is Traefik's web entrypoint, and that entrypoint answers *every* request with its own redirect:

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:32080/ping
301
$ curl -sk -o /dev/null -w '%{http_code}\n' https://localhost:32443/ping
404      # Traefik's ping lives on the `traefik` entrypoint, which the Service did not expose

Traefik's own --ping handler is on the traefik entrypoint (:8080), which nothing exposed. Rather than relaxing the matcher to 301 -- which would assert only "something is listening" -- that entrypoint is now published as NodePort 32081 and both target groups health-check http://<node>:32081/ping for 200. The chart warns in as many words that this port should not be exposed on a production deployment, because it hosts /dashboard/ and /api; api.dashboard is set to false, so the exposed entrypoint answers exactly one path. No document in this repo reads the Traefik dashboard -- the dashboards story is Grafana's.

$ kubectl get svc traefik -n traefik -o jsonpath='{range .spec.ports[*]}{.name}:node{.nodePort}{" "}{end}'
traefik:node32081 web:node32080 websecure:node32443
$ aws elbv2 describe-target-health --target-group-arn ...tf-https
  i-04d2feb020ccb3d6a  healthy    i-081186d2cd5668fe2  healthy
  i-08dbd7c33ed1deea5  healthy    i-015ea1031b2a671a7  healthy

Two smaller chart defects went with it: frontendHost/grafanaHost/jenkinsHost were read by templates/routes.yaml but never defined, rendering Host(); and Traefik was a DaemonSet asking for one RWO local-path PVC, which pinned three of four pods Pending with didn't find available persistent volumes to bind. persistence.enabled: false sends the chart back to emptyDir on /data, which is correct for a proxy that holds no state worth a volume. ACME on a DaemonSet is impossible, and that shaped the design

Decisions worth recording, because each was a real fork

  • Pre-sampling fan-out. Feeding spanmetrics from the sampled pipeline would have made the

error ratio a lie (100% of errors counted, 10% of successes) and the rate a tenth of the truth. The cost is a second pipeline's memory_limiter/batch, at 192Mi per replica.

  • Single producer per metric family, enforced by splitting the two producers between Tempo

(service-graphs only) and the collector (spanmetrics only).

  • The dashboard is a .yaml, not a .json. The repo convention's .json files cannot carry

the grafana_dashboard: "1" label the sidecar selects on, and a bare .json is invisible to scripts/check-dashboards.py. The JSON lives inside the ConfigMap and the parser reads it from there.

  • Loki's derivedFields stays []. Pointing Tempo traces at Loki needs a

traceID→log pattern this platform's Loki (3.x) query syntax has to be verified against, not guessed; the comment says exactly what would be added and why it is not there yet.

  • Policy satisfied, never waived. Tempo's first values had CPU 250m/1 — conftest rejected

it (Guaranteed QoS), and the values were changed to 250m/250m. policy/resources.rego is byte-identical to before this phase.

  • scripts/check.sh now kubeconforms the rendered Tempo chart, the same treatment traefik

already got: the chart's sources are Go template text and its ServiceMonitor/ PrometheusRule are CRDs, so the render is the only place they can be schema-checked.

Cost, moved by one line

scripts/cost-estimate.sh's CPU-credit model reads MEASURED_REQUEST_MILLI, which was 3600 and is now 3850 (measured, from the same render). The committed cost is unchanged — instances are priced by shape, not by requests — but the modelled worst case moved:

  platform requests      3850m  (admission guarantee only)
  worst case sustained   3850m  = requests fully used -> $82.12/mo surcharge risk
  !! total incl. worst case $179.87/month  $254.42 over 43 days - OVER the $200 credit

The worst case was already over the credit ($170.74 / $241.51); Phase 11 widens that gap by $12.91. Expected sustained (1280m, 80% of the t3 baseline under demo traffic) is unchanged at $0.00 surcharge.
