The headline number, stated plainly because it is the one that matters: the platform does not fit on one t3.medium. docs/resource-budget.md holds the arithmetic — 3600m / 4048Mi of requests against 1830m / 3741Mi schedulable = 196.7% CPU and 108.2% RAM, of which 2820m is the boutique namespace's own request, not the observability stack. The fix is architectural: all four nodes are schedulable, the k3s servers carry no control-plane taint, because with a hard 8-vCPU quota there is no separate worker fleet to pair a control plane with (kubeadm control-plane nodes are schedulable by default; EKS taints them). That gives 7320m / ~9042Mi, roughly 50% headroom on both axes.
